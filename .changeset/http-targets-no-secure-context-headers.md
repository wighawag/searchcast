Requests to plain `http://` URLs now carry the headers Chromium was measured to send there (`work/notes/findings/http-target-headers.md`) instead of the `https` tables. They go over HTTP/1.1, as Chrome's do: no `Upgrade: h2c` attempt (which the impersonation target made libcurl send), `Host` then `Connection: keep-alive` first, no `priority`, and Chrome's HTTP/1.1 spelling of each name (`User-Agent`, `Sec-Fetch-Site`, but `sec-ch-ua`; author headers keep the spelling the recipe gave them). To a host that is not a loopback one (anything but `localhost`, `*.localhost`, `127.0.0.0/8` and `[::1]`, which Chrome treats as potentially trustworthy) they carry no client hints and no `sec-fetch-*` (a CORS preflight keeps `sec-fetch-mode`), `accept-encoding: gzip, deflate`, and author headers right before `accept`. A `fetch` or `script` request from an `https` page to such a URL is mixed content, which Chrome blocks, so it is now refused with a `recipe` error before anything is sent; from an `https` page to a loopback `http` URL there is no `referer`. `https` tables are unchanged. `headerTable` and `preflightTable` give these tables when their `url` is `http://`.
