# Decisions made while building libcurl-platform-packages (2026-09-30)

Recorded for the `libcurl-platform-packages` done record. Reality check first: the task's premises held (the pins in `packages/searchcast/src/libcurl.ts`, `fetchLibrary`-less `install.ts`, `tar.ts`, `doctor.ts`, `data-dir.ts`, the `LibrarySource` names of the forward-note, `scripts/pack-check.mjs` with `PUBLISHABLE`, `scripts/no-skips.mjs`, both workflows). Live check (the one allowed): the pinned linux-x64 archive downloaded on 2026-09-30 hashes to its pin (`18b22585...f1`), and so do the darwin-arm64 and win32-x64 archives (downloaded only to inspect what their libraries link, see decision 1); the library built through the new script loads through the platform-package lookup and `searchcast doctor` reports impersonation active.

1. **OWNER REVIEW BEFORE THE VERSION PACKAGES PR: the license notices cover more than the three components the task named, and the Linux builds contain LGPL code.** The task asked for curl-impersonate, curl and BoringSSL. The library statically links more (read from curl-impersonate v2.1.1's `CMakeLists.txt` and `Makefile`, and confirmed in the binaries: the linux-x64 `curl_version()` is `libcurl/8.21.0-IMPERSONATE BoringSSL zlib/1.3.1 brotli/1.2.0 zstd/1.5.7 libidn2/2.3.7 nghttp2/1.63.0 ngtcp2/1.20.0 nghttp3/1.15.0`; the macOS and Windows libraries contain the same except libidn2, which curl-impersonate enables on Linux only). Each package's `LICENSE` therefore carries the upstream texts of all of them, verbatim, each under the URL it was taken from at the pinned tag or commit (curl-impersonate v2.1.1 `LICENSE`, curl `curl-8_21_0` `COPYING`, BoringSSL `156c7b75...` `LICENSE` (Apache-2.0 only at that commit), nghttp2 v1.63.0, ngtcp2 v1.20.0, nghttp3 v1.15.0 `COPYING`, brotli v1.2.0 and zstd v1.5.7 `LICENSE`, zlib v1.3.1 `LICENSE`; on Linux also libidn2 2.3.7's `COPYING`, `COPYING.LESSERv3`, `COPYINGv2`, `COPYING.unicode` from `https://ftp.gnu.org/gnu/libidn/libidn2-2.3.7.tar.gz`, and the GPL v3 text from `https://www.gnu.org/licenses/gpl-3.0.txt`, which the LGPL v3 supplements and the tarball does not ship). libidn2 (with the libunistring parts it includes) is LGPL-3.0-or-later OR GPL-2.0-or-later: publishing the Linux packages makes this repo a distributor of LGPL code in a combined work. The `LICENSE` header gives the source location (curl-impersonate's tag, which builds every component, and the libidn2 tarball) and says the library is a replaceable shared library (`SEARCHCAST_LIBCURL_PATH`), which is the good-faith reading of the LGPL's source and relinking terms; it is not legal advice, and the owner should confirm it is acceptable before the first publish. Alternatives: only the three named texts (rejected: incomplete, and the MIT/BSD components require their notice in binary redistributions); not shipping the Linux packages (rejected: that is the main platform). Touches: the five `packages/libcurl-*/LICENSE` files, their `license` fields, `scripts/pack-check.mjs` (`LIBCURL_LICENSE`, `LIBCURL_LINUX_LICENSE`).
2. **`license` is an SPDX expression**, not `SEE LICENSE IN ...`: `MIT AND curl AND Apache-2.0 AND BSD-3-Clause AND Zlib` for macOS and Windows, plus `AND (LGPL-3.0-or-later OR GPL-2.0-or-later) AND Unicode-DFS-2016` for Linux (zstd is dual BSD/GPL-2.0 and is taken under BSD-3-Clause). Machine-readable for license checkers, and still honest; the texts are in `LICENSE`. This repo's own files in those packages (README, package.json) carry no code, so no AGPL is claimed. The notices file is named `LICENSE` (one file, sectioned) so the pack check's "every tarball has a LICENSE" rule holds unchanged.
3. **The notices are committed in each package (five copies, two variants)**, not generated at pack time: the pack check must pass on a checkout without a build, and a test keeps the copies identical per variant.
4. **Pack check without the payload** (the forward-note's question): `scripts/pack-check.mjs` packs the platform packages with `--config.ignore-scripts=true` (their `prepack` is the refusal) and accepts the tarball with or without the library (`payload`), nothing else; `release:ci` runs it with `--require-payloads`, so at release every library must be packed. Each package's `prepack` (`node ../../scripts/libcurl-packages.mjs check`, not an install script) refuses to pack unless the library is there, a `.payload.json` stamp written by the build names the current pinned archive and sha256, and the library's sha256 matches the stamp (catches a stale build after a pin change). The stamp is gitignored and not packed. The pack check also now rejects `preinstall`/`install`/`postinstall` scripts in every package.
5. **The release builds all five payloads on every release run, before the changesets step**, whether that step then opens the Version Packages PR or publishes: simplest, and a run that publishes always has the full set built from the pins (a failed download or checksum fails the job before any publish; the build also fetches and verifies every archive before writing any, so it is all or nothing). Cost: five downloads (about 30 MB each) per push to main. Alternative: build only when no changeset is pending (rejected: duplicates changesets' own decision and is easy to get wrong).
6. **The build reuses `searchcast install-libcurl`'s code**: `install.ts` gains `fetchLibrary(platform, options)` (download through the proxy only, sha256 before unpacking, `extract` of the pinned regular-file entry within the same size caps), which `installLibcurl` now calls; the script imports it from searchcast's build (`dist/install.js`), so it needs `pnpm build` first. `fetchLibrary` is not exported from `searchcast/install` (internal: the public API is unchanged). The payload's name is the data directory's `libraryFileName` for the package's OS (a test ties `payloadFile` in the script to it).
7. **The lookup** is `platformPackageLibrary(from, platform)` in `libcurl.ts`: `createRequire(import.meta.url).resolve('<name>/package.json')`, then the library file next to it; any resolution failure, a platform without a pin, or a missing file is "not installed" (skipped). The packages have no `main`/`exports`, so `<name>/package.json` stays resolvable. `locateLibrary` gained an optional third parameter `from` (tests); the public `resolveLibraryPath(option, env)` is unchanged. `LocatedLibrary` and the doctor report's `library` gain `package: {name, version}` for this source; `formatReport` prints `from: the platform package <name> <version> (installed with searchcast)`.
8. **The not-found message** (the `impersonation` error's how-to-fix, shown by `doctor` and every failed load) now names the platform package on a pinned platform and says `install-libcurl` is for skipped optional dependencies; on an unpinned platform it says there is neither. `install-libcurl`'s own "no pinned archive" message says there is no platform package either, and `searchcast --help` says the command is only needed where npm did not install the platform package.
9. **Tests that need "no library anywhere" hide the platform packages**, since the workspace links all five into searchcast's `node_modules` and CI builds linux-x64's: CLI runs use the existing `test/hide-modules.mjs` preload (it also hides `require.resolve`), in-process tests mock `node:module` (`test/hide-platform-packages.ts`). The lookup's own tests confine resolution to their temp dir because pnpm's `NODE_PATH` also reaches the workspace packages. Nothing in production is test-only.
10. **`scripts/no-skips.mjs` only expects a report from packages with a `test` script** (the platform packages have none: they carry no code, and their library is tested from searchcast).
11. **`scripts/libcurl-packages.mjs` compares `process.argv[1]` and its own path through `realpath`** before running its CLI, so the `prepack` guard also runs when the scripts directory is reached through a symlink (the test does exactly that; with the plain `resolve` comparison of the other scripts it silently did nothing, see the observation `2026-09-30-scripts-cli-guard-symlink.md`).
12. **CI keeps its `install-libcurl` step** (it sets `SEARCHCAST_LIBCURL_PATH` for the native tests and exercises the real command) and adds `node scripts/libcurl-packages.mjs build linux-x64` before the tests; `platform-package-native.test.ts` then runs `doctor` and a `query` with nothing configured. It skips (with a notice from `test/native-notice.ts`) where the payload is not built, which the no-skip check forbids in CI.
13. **Glossary:** `CONTEXT.md` gains **Platform package**. README (root, which is `searchcast`'s) documents install through the platform package, the lookup order, the release build and the LOC rows of the modules touched here.
14. **Retry after PR #17 (the CI-only failure of doctor's native "with remote" test): test isolation, not the lookup.** Cause, reproduced locally with the linux-x64 package built and `SEARCHCAST_LIBCURL_PATH` set as in CI: in `packages/searchcast/test/doctor.test.ts`, the in-process `doctor({env})` of "says nothing about the old directory ..." found no library in the temp data directory, so it fell through to the platform package that CI builds, loaded it, and the library is loaded once per process; the later in-process `doctor({libcurlPath: LIB})` was then refused ("already loaded from ..."), so `impersonating` was false. Fix: the file now mocks `node:module` with `hidingPlatformPackages` like `libcurl.test.ts` (the CLI runs already used `HIDE_ARGS`), the old-directory test asserts `report.library` is undefined (so any future leak fails there, in the no-native block, even locally with a built payload), and the native assertion prints `report.problem`. Alternative rejected: making the lookup skip the platform package when an explicit path is used later (the process-global load is intended, ADR 0001/0002, and would still refuse a second path). Touches only that test file.
