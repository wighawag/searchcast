# Decisions made while building serve-options-before-command (2026-09-30)

Recorded for the `serve-options-before-command` done record. Reality check first: the task's premises held. `packages/searchcast/src/browser-cli.ts` delegated only on the first argument (decision 2 of `2026-09-30-searchcast-serve-command-decisions.md`), `@searchcast/browser/cli` exported only `runCli`, the option table lived inline in its `main`, and the pending `searchcast` changeset and the root README both carried the "command must come first" sentence. This reverses that decision 2, in the way it named.

1. **The export is `browserCommand(argv): string | undefined`** on `@searchcast/browser/cli`, the first positional under the runner's own option table (hoisted to one `OPTIONS` constant that `runCli` also parses with), or `undefined` when there is none or argv does not parse. It does not check the command against the known ones; the `searchcast` bin decides which it delegates (`serve`, `browser-query`, not the `query` alias, which is the HTTP query on that bin). Code site: `packages/browser/src/cli.ts`. Touches: the `./cli` entry's API (its export test now lists both names).
2. **When the delegation after options is tried**: only when the first argument starts with `-`, the HTTP parser either throws or finds no HTTP command as the first positional (`Object.hasOwn(COMMANDS, ...)`), and `serve` or `browser-query` appears literally in argv. The last condition is exact (a positional is an argv element), and it keeps `@searchcast/browser` from being imported for plain HTTP usage errors and `--help` (the existing "HTTP commands do not need it" test). When the browser table does not find a browser command (for example `--no-such-option serve`), the HTTP parser's usage error is reported as before. Alternative considered: always import the package when the HTTP parse fails; rejected, it would load an optional package for every typo. Code site: `packages/searchcast/src/cli.ts` and `runBrowserCliAfterOptions` in `browser-cli.ts`.
3. **Missing `@searchcast/browser` with options first**: the package cannot be asked where the command is, so the first `serve` or `browser-query` word in argv is taken as the command, and the usual missing-package line (exit 1) names it. This can misname only an argv that is invalid for the HTTP commands anyway (for example `--profile serve x`, where `serve` is a value), and it tells the user what to install either way. Alternative: fall back to the HTTP usage error; rejected, the acceptance wants the missing-package line reached through that order, and a usage error would hide the real fix. Touches: the missing-package message (unchanged text, from decision 1 of the serve-command note).
4. **Changesets**: no second changeset for `@searchcast/browser`; its pending first-release changeset (`browser-library-package.md`) gained one sentence naming `browserCommand`, since that release is where the export first ships. The `searchcast` changeset lost its "command comes first" sentence, and so did the root README; `packages/browser/README.md` documents `browserCommand`.
