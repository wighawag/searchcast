# Decisions made while building recipe-package-rename (2026-09-30)

Recorded for the `recipe-package-rename` done record. Reality check first: the task's premises held. `packages/recipe` was `serpcast-recipe` 0.2.0 with the two entries, `packages/searchcast` depended on it via `workspace:*`, `packages/browser` pulled `serpcast-recipe ^0.1.0` from npm, and the lockfile carried that npm entry. No meaning or message of the schema changed: `src/recipe.ts` changed only in comments, and every recipe test is unchanged apart from the package name and two temp-dir prefixes.

1. **`CHANGELOG.md` added to the recipe package's `files`.** npm and pnpm do not pack a CHANGELOG automatically (only README, LICENSE and package.json), and the acceptance criterion lists it in the expected pack content. Alternative: leave `files` as `["dist"]` and drop CHANGELOG from the expectation; rejected because the criterion names it and the `monorepo-ci-and-release` pack check expects the same shape (dist, README, LICENSE, CHANGELOG, package.json) for every package. The other packages will need the same line when that check lands.
2. **Root `README.md` and `CONTEXT.md` still say `serpcast-recipe`.** They are docs (excepted by the first criterion), and the `rename-serpcast-to-searchcast` task rewrites both ("The root README becomes the monorepo's README ... CONTEXT.md uses the new names"). Until then the root README's code samples (`import ... from 'serpcast-recipe/node'`) show the old name. The browser package README's line 82 still says "serpcast" for the HTTP runner; that README is rewritten by `browser-library-package`. Only its `serpcast-recipe` links were updated here.
3. **Fixture strings left as is:** `packages/searchcast/test/copy-publish-assets.test.ts` still uses `packages/serpcast-recipe` as arbitrary link paths to exercise `rewriteReadmeLinks` (it tests the rewriting, not the package), and `install-recipes.test.ts` uses a `serpcast-recipes-` temp-dir prefix unrelated to this package. Both belong to the searchcast rename task. The test titled "rejects %s with the searchcast message" keeps its title: "searchcast" there already means the browser runner's original messages, and the title is history, not a package name.
4. **Comments name the runners per ADR 0005:** `searchcast` for the HTTP runner, `@searchcast/browser` for the browser runner, with the extraction source written as "the browser runner's `src/recipe.ts` (searchcast@0.1.1, now @searchcast/browser)" so the historical version stays accurate.
5. **Dependency spec `workspace:^`** in both importers, as the task asked (`packages/searchcast` moved from `workspace:*`); its `dependencies` were re-sorted so the scoped name comes first, as pnpm writes them. The `searchcast >=0.1.1` optional peer of `packages/searchcast` is untouched (the serve/browser tasks own it).
6. **A new `test/package.test.ts`** pins the manifest name, `packageName`, MIT, the LICENSE file, no `dependencies`/`peerDependencies`/`optionalDependencies`, the two entries, and the export lists of both entries (taken from serpcast-recipe 0.2.0).
