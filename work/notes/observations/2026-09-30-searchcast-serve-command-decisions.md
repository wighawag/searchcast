# Decisions made while building searchcast-serve-command (2026-09-30)

Recorded for the `searchcast-serve-command` done record. Reality check first: the task's premises held, with the conductor's forward-note already applied. `runCli(argv)` from `@searchcast/browser/cli` accepts `serve`, `browser-query` and `query` and carries 0.1.2's top-level error handler; `packages/searchcast` already had the `@searchcast/browser` `workspace:^` devDependency and the optional peer `>=0.1.0 <0.2.0`; the CLI end-to-end tests had no TCP case (the six cases are: Unix socket with ephemeral profile and idle exit, no-loopback via `browser-query`, `--listen systemd` refusal, socket activation, Xvfb, SearXNG). All six moved and pass through the real bin (run locally with a Nix-store Chromium and Xvfb, and the SearXNG case with a stub `searx` package; the stub is not committed).

1. **Missing `@searchcast/browser` exits with 1**, with one line: `searchcast: <serve|browser-query> needs @searchcast/browser, which is not installed: install it next to searchcast (npm install -g @searchcast/browser)`. Why 1: the bin's convention is 0 success, 1 a failure, 2 a usage error; the command line was right, the machine lacks a package (like a failed install). Alternative: 2, which is what the browser runner uses for everything (usage and runtime errors alike), rejected because the missing package is not something the browser runner decides and the searchcast bin's own convention applies to its own messages. Only the package itself missing gets this line (`ERR_MODULE_NOT_FOUND` naming `'@searchcast/browser'`); any other import failure (a broken install, a missing transitive dependency) falls to the bin's generic handler (stack on stderr, exit 1). Touches: the `searchcast` bin's exit-code doc (README, `cli.ts` header). Code site: `packages/searchcast/src/browser-cli.ts`.
2. **The browser command must be the FIRST argument.** 0.1.2 parsed with `parseArgs`, so `searchcast --headless serve ...` also worked; now only `searchcast serve ...` (as the README, the usage line and every systemd unit write it) is delegated, and options before the command reach the HTTP commands' parser, which refuses them (exit 2). Why: recognising the command anywhere needs the browser runner's option table (which flags take a value) in the `searchcast` bin, a copy that would drift, or a new export on `@searchcast/browser/cli` (its API is fixed at `runCli` by `browser-library-package` and its test). Alternatives: copy the option table (rejected, drift); add an export (rejected, another task's API). Touches: `searchcast serve` compatibility for an unusual argv order; documented in the README upgrade note and the changeset. Reversible later by adding that export.
3. **The browser's `cli-usage.test.ts` stays in `packages/browser`**, run through an inline `node -e` import of the built `./cli` entry instead of the deleted launcher, and a bin-level `packages/searchcast/test/serve-usage.test.ts` was added. Why: `runCli`'s own contract includes the unknown-command message and the `query` alias, which the bin no longer reaches (it only delegates `serve` and `browser-query`), so they can only be tested at the library level. The launcher file itself is deleted, as the task says.
4. **koffi is proven not loaded by hiding it**: `packages/searchcast/test/hide-modules.mjs` is a `node --import` preload (`module.registerHooks`, Node 22.15+/24) that makes chosen packages fail to resolve like a missing package and logs every attempt. Every serve end-to-end case runs with koffi hidden (so each one also proves `serve` works with no koffi), and every bin usage case asserts koffi was never even asked for. libcurl-impersonate is only ever loaded through koffi (`koffi.load` in `libcurl.ts`), so no koffi means no libcurl. The same preload hides `@searchcast/browser` for the missing-package test. The HTTP commands' modules are still imported statically by `dist/cli.js` (they import koffi lazily, which is what the test pins).
5. **The e2e test imports the browser package's fixture site** (`../../browser/test/fixture.js`) rather than a copy: one fixture for `packages/browser/test/browser.test.ts` and `packages/searchcast/test/serve.test.ts`. Test code only, not shipped.
6. **Pack test uses `npm pack --dry-run --json --ignore-scripts`** (`test/pack.test.ts`): lists the files without writing and without running `prepack`. It asserts `integrations/searxng/searchcast.py` is in the tarball at that path and is the only `integrations/` file. `files` names the one file, not the directory, so a `__pycache__` can never ship.
7. **Changeset: `searchcast` minor only.** The browser package's published content changes only in its README (serve docs replaced by a pointer); its pending minor changeset from `browser-library-package` already covers the release, and a second one would only add a changelog line.
8. **Also touched:** a comment in `.github/workflows/test.yml` (the Chrome env now also serves the serve tests in `packages/searchcast`), and the root README Develop section (which tests need Chrome, Xvfb, `systemd-socket-activate`, `unshare`, a SearXNG Python).

Observation, outside this task: the SearXNG end-to-end case needs `SEARCHCAST_TEST_SEARXNG_PYTHON`, which CI does not set, so it never runs in CI (before or after the move). `monorepo-ci-and-release` may want to install SearXNG (or a stub `searx.exceptions`) in the test job.
