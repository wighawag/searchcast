# Decisions made while building browser-library-package (2026-09-30)

Recorded for the `browser-library-package` done record. Reality check first: the task's premises held. `packages/browser` was `searchcast` 0.1.2 with a `searchcast` bin, its `src/index.ts` and `src/cli.ts` byte-identical to the `v0.1.2` tag, `@searchcast/recipe` already a `workspace:^` dependency (from `recipe-package-rename`), and `packages/searchcast` (still `serpcast`) had the optional peer `searchcast >=0.1.1`, resolved from npm (0.1.1) in the lockfile. One small drift: the task lists a TCP case among the existing CLI tests, but `test/cli.test.ts` had none (its cases are the Unix socket with ephemeral profile and idle exit, no-loopback, `--listen systemd` refusal, socket activation, Xvfb, SearXNG). Every existing case now runs through the launcher; no TCP case was added, since the criterion is "every case that existed".

1. **The optional peer is `@searchcast/browser: ">=0.1.0 <0.2.0"`, plus a `workspace:^` devDependency** in `packages/searchcast`. Why: with a `workspace:^` peer, `changeset status` plans `serpcast` at **1.0.0** (changesets bumps a peer dependent to major whenever the peer gets a minor, `onlyUpdatePeerDependentsWhenOutOfRange` being off), which the spec forbids. With the explicit range, the workspace version 0.0.0 does not satisfy it, so changesets leaves the edge out of its graph (it prints `Package "serpcast" must depend on the current version of "@searchcast/browser": "0.0.0" vs ">=0.1.0 <0.2.0"` as a warning, which goes away once the Version Packages PR sets 0.1.0) and the plan is `@searchcast/browser` 0.1.0, `@searchcast/recipe` 0.1.0, `serpcast` 0.6.1 (patch, from the recipe dependency), no major. A range alone makes `pnpm install` look for `@searchcast/browser@>=0.1.0 <0.2.0` on npm (only 0.0.0 exists) and fail, hence the `workspace:^` devDependency, which pnpm links and which satisfies the peer in this workspace (the real-import test in `packages/searchcast/test/browser.test.ts` uses it). Alternatives: `workspace:^` peer (plans 1.0.0, rejected); changing `.changeset/config.json` to `onlyUpdatePeerDependentsWhenOutOfRange` (touches the release config owned by `monorepo-ci-and-release`, rejected here). Touches: `searchcast-serve-command` (which planned to add this same devDependency: it is already there) and `monorepo-ci-and-release` (see the hazard below).
2. **Hazard for `monorepo-ci-and-release`:** once `@searchcast/browser` is 0.1.x and inside the peer range, a later MINOR changeset on `@searchcast/browser` will make changesets plan a MAJOR for `searchcast` (same peer rule). The release-plan check that task adds will catch it; the fix is then either that config flag or releasing the peer range change together. Nothing to do in this task.
3. **`version` set to `0.0.0`** as the task's metadata paragraph says, although the spec's shared rules say not to edit `version` fields. The task is explicit, the recipe task did the same (0.2.0 to 0.0.0), and keeping 0.1.2 would make the minor changeset yield 0.2.0 instead of the 0.1.0 of ADR 0005.
4. **`runCli` accepts both `browser-query` and `query`** for the one-shot query. The task says `runCli` takes the 0.1.2 arguments (`query ...`) and also that the tests use the `browser-query` spelling; accepting both satisfies both, keeps every error message byte-identical (`query needs --recipe <file>`, `query needs a query`), and lets the `searchcast` bin pass `browser-query ...` through unchanged (`searchcast-serve-command`). Only the usage line changed. Alternative: only `browser-query` (breaks an argv written for 0.1.x) or only `query` (the bin would have to rewrite the command name). Recorded in the module comment of `packages/browser/src/cli.ts`.
5. **`runCli(argv)` includes the 0.1.2 top-level error handler** (`RecipeError` and `SearchcastError` become `searchcast: ...` and exit 2), so a caller gets exactly the 0.1.2 bin behaviour by calling it; it resolves when the command is running or done, like the old `main`. The shebang was dropped (no bin).
6. **LICENSE committed** in `packages/browser` (a verbatim copy of the root AGPL-3.0 LICENSE) rather than copied at pack time. `scripts/copy-publish-assets.mjs` copies the root README too, and this package has its own README; committing avoids a second mode in that script (which the `rename-serpcast-to-searchcast` task edits). Cost: two copies of the same text to keep identical, which the AGPL text makes a non-issue.
7. **`files` is `dist` + `CHANGELOG.md`** (npm adds README, LICENSE, package.json): `src` and `integrations/searxng/searchcast.py` left the tarball. The engine file stays in the repo at `packages/browser/integrations/` (the task says it moves with the serve command); nothing is published between the two tasks. Pack dry-run verified by hand: CHANGELOG.md, LICENSE, package.json, README.md, and 36 `dist/` files. No automated pack test here; `monorepo-ci-and-release` adds the pack check for every package.
8. **Scripts:** removed `release`, `release:ci`, `prepublishOnly`, `changeset:check` and the `@changesets/cli` devDependency (the root owns releasing); kept `format`/`format:check` and `prettier`, which are not about releasing.
9. **Launcher imports `@searchcast/browser/cli` by self-reference**, so the `./cli` subpath of `exports` is what the end-to-end tests exercise, not a file path.
10. **New Chrome-free tests** (`test/package.test.ts`, `test/cli-usage.test.ts`): the export list of 0.1.2, no bin, entries, metadata, nothing run on import, the full usage text (0.1.2's with the one line changed), each usage error with its exact message and exit 2, the `--listen systemd` refusal before anything starts, and both query spellings. They run in the local gate, where the Chrome tests are skipped. The Chrome tests were also run locally with a Nix-store Chromium (all pass; Xvfb and SearXNG cases skipped for lack of those tools).
11. **README:** a library README (what it is, `new Searchcast`, errors, the recipe pointer, the `./cli` entry). It keeps the HTTP API, the options table and the systemd example under the `./cli` section, since the `searchcast` README gains them only in `searchcast-serve-command`; that task can then shorten this section to a pointer. The root README's library-mode paragraph now names `@searchcast/browser` and its install line (the error text it quotes changed); the rest of the root README is left to the rename task.
12. **PR note for `rename-serpcast-to-searchcast`:** its 0.2.0 changeset should mention that the optional peer is now `@searchcast/browser` (`>=0.1.0 <0.2.0`) instead of `searchcast`, and that the missing-peer error says `npm install @searchcast/browser`.
