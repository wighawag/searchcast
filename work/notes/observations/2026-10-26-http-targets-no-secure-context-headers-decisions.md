# Decisions: plain http:// targets (task `http-targets-no-secure-context-headers`)

2026-10-26. Choices made while making the header tables (`packages/searchcast/src/chrome.ts`) and the transport (`packages/searchcast/src/transport.ts`) follow the finding `work/notes/findings/http-target-headers.md`.

1. **The rule is "potentially trustworthy", not "the scheme is http".** The task's premise ("Chrome sends no `sec-fetch-*` and no client hints to a non-secure origin") held for ordinary host names, but the capture showed that `http://localhost`, `http://foo.localhost`, `http://127.0.0.1` and `http://127.0.0.2` DO get every secure-context header (they are potentially trustworthy in the Secure Contexts sense). So `isPotentiallyTrustworthy(url)` (chrome.ts, exported from that module only, not from the package index) decides: `https:`, or `http:` to `localhost`, `*.localhost`, `127.0.0.0/8` or `[::1]`. `[::1]` comes from the same Chromium rule (`net::HostStringIsLocalhost`) but was not captured. Alternative: drop the headers for every `http:` URL, rejected as it would be wrong for exactly the URLs a local test or a local service uses. CONTEXT.md gains a short "Potentially trustworthy" entry so the term is not re-invented.

2. **Every `http:` target is HTTP/1.1, spelled as Chrome spells it there.** The header table returned for an `http:` `url` carries the wire spelling (`User-Agent`, `Sec-Fetch-Site`, `sec-ch-ua`), `connection: keep-alive` first and no `priority`, so `headerTable()` still equals the wire (minus `Host`, which libcurl sends). Alternative: keep lowercase names in `headerTable` and re-case in the transport, rejected because the table would then no longer be "the exact headers sent". Touches: `headerTable` and `preflightTable` callers that look headers up by lowercase name (the transport now looks up `access-control-request-headers` case-insensitively).

3. **An explicit POST `contentType` is spelled `Content-Type` on HTTP/1.1.** Chrome keeps whatever spelling the page's script used (`content-type` and `Content-Type` were both captured), and the `contentType` option carries no spelling. `Content-Type` is what Chrome itself writes for a string body without one, and a common script spelling. Alternative: `content-type`, equally real; or a new option to choose, rejected as surface for no measured need. Author headers, which DO carry a spelling (the record's keys), keep the one the recipe gave (the first, when two differ only in case).

4. **A `fetch`/`script` from an `https` page to a non-trustworthy `http` URL is refused (`recipe` error, nothing sent).** Chrome blocks it as mixed content (captured: the request never reached the server), so there is no table to send; inventing one (the http table without `referer`) would be a guess at a request Chrome never makes. This is a NEW refusal: a code recipe that did this before got the `https` table sent over `h2c`. It follows the existing "Not measured, so not offered" / "as in the browser" rule (POST on a non-fetch kind, an unmeasured author-header set, a refused preflight). The task's acceptance "the referer downgrade case sends no `referer`" is met by the case Chrome does send: an `https` page to a loopback `http` URL (`fetch`, `script`, preflight), which goes without `referer`. Navigations are not checked: `same-origin-navigation` is same-origin by definition, and a cross-origin navigation is not a modelled kind. Touches: `session.request`, a code recipe's `ctx.http` (README "Plain `http://` URLs").

5. **libcurl gets `CURLOPT_HTTP_VERSION = CURL_HTTP_VERSION_1_1` for `http:` URLs only.** The impersonation target made libcurl try an `h2c` upgrade (`Upgrade: h2c`, `HTTP2-Settings`, `Connection: Upgrade, HTTP2-Settings`), which Chrome never sends. Alternative: `CURL_HTTP_VERSION_2TLS` for every request, rejected to leave the `https` path byte-for-byte as it was.

6. **`Host` + `Connection` as one custom header line.** libcurl moves a custom `Connection:` header to the end of an HTTP/1.1 request but sends a custom `Host:` first, so the transport sends `Host: <url host>\r\nConnection: keep-alive` as the first `CURLOPT_HTTPHEADER` entry when the table starts with `connection`. The host comes from the WHATWG URL parser (no CR/LF possible). Alternative: let `Connection` go last and record the difference, rejected because the header order is the point of the impersonation and the exact order is reachable. If a future libcurl rejects the embedded CRLF, the native http-target tests (exact raw header list) fail.

7. **The transport computes the cookies' site itself** (`fetchSite` override, else `fetchSite(url, referer)`, for `fetch`/`script`; same-origin for navigations), instead of reading `sec-fetch-site` back out of the table (decision 1 of `2026-10-26-cookies-respect-samesite-decisions.md`): a non-trustworthy `http` target's table has no `sec-fetch-site`. Same computation and override as the table's, so the two still cannot disagree; the first `headerTable` call still validates the request before the jar is read.

Out of scope and noted in the finding's "Not measured": `https` over HTTP/1.1 (a server without HTTP/2) still gets lowercase HTTP/2 names, and an `http` target through an HTTP proxy was not compared.
