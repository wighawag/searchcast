# Decisions: cookies respect SameSite (task `cookies-respect-samesite`)

2026-10-26. Choices made while storing `SameSite` in the cookie store (`packages/searchcast/src/cookies.ts`) and filtering cross-site requests (`packages/searchcast/src/transport.ts`). Backing: the finding `sec-fetch-site-by-initiator` (cross-site `fetch` with credentials and `script` sent only the `SameSite=None; Secure` cookie) and Chrome's documented defaults (Lax by default, None requires Secure).

1. **The site for cookies is the header table's own `sec-fetch-site`.** The transport builds the table once without a cookie, reads its `sec-fetch-site`, and asks the jar for `crossSite: site === 'cross-site'`. So the `fetchSite` override moves the cookies too (`fetchSite: 'cross-site'` drops non-`None` cookies, `fetchSite: 'same-site'` sends them all), and the cookies can never disagree with the label. Alternative: a separate site computation for cookies (Chrome's "site for cookies" is a separate concept), rejected because the transport only knows one page per request and two computations could drift. Touches: the `fetchSite` request option (README, CONTEXT.md "Fetch site").

2. **`document` and `same-origin-navigation` are never cross-site for cookies, so they send `Strict` cookies too.** `document` is a typed navigation (`sec-fetch-site: none`); Chrome treats a browser-initiated navigation as same-site for cookies. `same-origin-navigation` is same-origin by definition. The transport has NO cross-site top-level navigation kind, so the acceptance rule "a top-level navigation carries `Lax` and `None` cookies cross-site, not `Strict`" is implemented and tested in `CookieStore.header(url, now, {crossSite: true, topLevelNavigation: true})` only; the transport passes `topLevelNavigation` for the two navigation kinds, which today never combine with `crossSite`. If a cross-site navigation kind is ever added, it gets the rule for free. This rule is Chrome's documented behaviour, not measured (the finding lists page-initiated navigations as not measured).

3. **Not modelled: Chrome's "Lax+POST" exemption** (a cookie without a `SameSite` attribute, under 2 minutes old, is still sent on a cross-site top-level POST navigation). There is no cross-site navigation kind and no navigation POST, so it could not apply. A defaulted cookie and an explicit `SameSite=Lax` are therefore stored alike (`sameSite: 'Lax'`), not as a separate "unspecified" value. Alternative: store `undefined` for "unspecified" to keep the distinction; rejected as it would make an absent field mean two things (an old saved cookie vs a defaulted new one).

4. **Value spelling `'Strict' | 'Lax' | 'None'`** (the `Set-Cookie` and CDP/Playwright spelling), parsed case-insensitively; an empty or unknown value is `Lax` (Chrome ignores an unrecognised value, so the default applies). New exported types `SameSite` and `CookieRequestContext`.

5. **A saved cookie without the field is normalised to `Lax` on load** (`new CookieStore(saved)`), so `cookies()` returns it with `sameSite: 'Lax'`. The chain's `sameCookies` compares `sameSite ?? 'Lax'`, so an old saved list and the live session's normalised list still compare equal and the live session is reused.

6. **`SameSite=None` without `Secure` is rejected from `document.cookie` too** (`ctx.cookies.set` returns false), since it goes through the same `Set-Cookie` parser, as Chrome does.
