# Decisions made while building fetch-author-headers (2026-09-30)

Recorded for the `fetch-author-headers` done record. Code sites: `packages/searchcast/src/author-headers.ts` (new: the measured allowlist and its placement, and every refusal), `headerTable` and `preflightTable` in `chrome.ts`, `checkPreflight` and `PostOptions` in `post.ts`, `RequestOptions` and the preflight cache in `transport.ts`, `http` in `code.ts`, and `examples/recipes/marginalia.mjs`. Measurement: `work/notes/findings/fetch-author-headers.md`.

Reality check first: the task (as re-scoped by the conductor's retry handoff) matched the code. The first attempt's measurement (the observation `2026-09-30-author-header-order-is-hash-order.md`) was kept and a second run, local servers only, measured what the allowlist needs: `{api-key}` and `{authorization}` for GET and every POST body kind, at every fetch site, plus the preflight refusals and cache. Every measured case put the header right after `sec-ch-ua-platform`, so the table model expresses the allowlist exactly; no STOP was needed.

1. **Allowlist of name sets, not of names.** `PLACEMENT` in `author-headers.ts` maps a sorted, comma-joined lowercase name set to the table header it follows. Today both sets have one name, so "the set's wire order" is trivial; a later multi-name set needs its measured order in that map (the map's value would have to grow from "the slot" to "the ordered interleaving", since a larger set also moves `user-agent`). Alternative: reimplement WTF's hash; rejected (the conductor's option (b), and far too fragile).
2. **Refusal messages.** Each refusal is a `recipe` error naming the header: forbidden (the Fetch standard's list, `sec-*`, `proxy-*`, and the three `x-*-method-override` names, refused outright rather than only for a forbidden method value), table names (`user-agent`, `accept`, `accept-language`, `priority`, `upgrade-insecure-requests`, and `content-type`, which points to a POST's `contentType`), and an unmeasured set (names the supported sets and why). `accept-language` and `priority` can be set by a page's script, but a set `accept-language` moved in the measurement, so they are refused as table names rather than modelled. Touches: nothing outside this feature.
3. **Values.** Trimmed of leading/trailing space, tab, CR and LF as `fetch()` normalizes, then required to be non-empty printable ASCII (`[\t\x20-\x7e]+`), the same rule as a POST's `contentType`. Stricter than a browser in two ways: an empty value and a latin-1 byte above 0x7E are refused (a browser sends them). Chosen because libcurl gets the header as a C string (UTF-8 from JS, not the latin-1 bytes Chrome sends) and because an empty header needs libcurl's special `Name;` form, neither of which is measured or tested on the wire. Alternative: support both; left out until a recipe needs them.
4. **Duplicates combine, as Chrome does** (`{'API-Key': 'a', 'api-key': 'b'}` sends `api-key: a, b`, in insertion order). Only an object is accepted (no `Headers`, no array of pairs), to keep a plain-JS contract with one shape.
5. **Validated in three places, one implementation.** `authorHeaders()` runs in `code.ts` (so an injected transport, such as the tests' fake, gets checked and lowercased headers and the error carries the recipe's name), in `headerTable` and in `preflightTable` (so the public table functions and the transport refuse on their own). Only the set list and the `AuthorHeaders` type are exported; the checker stays internal.
6. **Preflight for GET.** `preflightTable` gained `method` and `headers`; its `method` defaults to POST when `contentType` is given, else GET, so every existing call keeps its meaning. The transport now computes a preflight for every `fetch` (it returns `undefined` when none is due), not only for a POST.
7. **Preflight cache semantics changed (measured):** an entry is now `{expires, allowed header names}`, a hit needs every requested name to be allowed, and a new preflight REPLACES the entry (Chrome's cache showed exactly that). For a POST without author headers this is the same as before (the entry always allowed `content-type`). `checkPreflight` now takes the requested names and returns `{maxAgeS, allowedHeaders}` (internal, not exported). The refusal message now says "does not allow the request from <origin>: <name> is not in access-control-allow-headers" instead of "the POST ... content-type is not ...". Touches: the `preflightCache`/`maxPreflightAgeS` options (docs now say "such request").
8. **Marginalia with a key: same-origin `fetch` from the API's own origin** (`referer: https://api2.marginalia-search.com/`). A page on `marginalia-search.com` would make it a same-site request, which Chrome preflights, and whether Marginalia's API answers a credentialed CORS preflight is unknown (not checked: no request to the real API was made). Same-origin needs no preflight. Alternative: the site's search page as referer; rejected for that reason. An empty `MARGINALIA_API_KEY` counts as unset (old API with `public`, as before). A key set in the environment now goes to the current API in a header, where before it went into the old API's URL; the README says so.
9. **ADR 0001 and CONTEXT.** ADR 0001 says every request carries only our header table; author headers sit inside it where Chrome places them, so the headers still describe the same Chrome as the TLS side. The ADR was not edited; CONTEXT.md's **Header table** entry names the exception and a new **Author header** entry defines it (checked against existing terms: "header table", "preflight"; no overlap). The observation note was kept (append-only bucket) with a pointer to the finding.
10. **Size discipline:** the new rules went into a new module `author-headers.ts` (186 LOC) instead of growing `chrome.ts` or `transport.ts` further; the rows touched in the README's LOC table were updated.
